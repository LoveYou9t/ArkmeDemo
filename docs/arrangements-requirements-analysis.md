# 即我「安排」模块需求梳理

## 1. 原始需求的核心判断

「安排」不是传统意义上的待办、日程、提醒、任务或项目管理模块的简单组合，而是一个更抽象的统一入口：承载所有“还没发生，但用户后续可能需要执行、关注、推进或交给 AI 处理”的事项。

它要解决的不是“让用户更严肃地管理任务”，而是让用户在真实生活和真实对话中，轻量、自然、低压力地看见和处理自己未来可能要面对的事情。

因此，这个模块的核心产品气质应该是：

- 统一但不僵硬：待办、日程、提醒、任务、规划都可以被归入“安排”，但不强迫用户先选择复杂类型。
- 智能但可修正：AI 可以自动识别、合并、补全、判断状态，但必须允许用户手动创建、编辑、合并、拆分和完成。
- 有序但不制造焦虑：它要帮助用户从混乱中看见重点，而不是把过期未完成事项堆成一片红色警告。
- 面向关系和上下文：安排往往来自人、对话、群聊、时间、地点和承诺，详情页需要保留相关上下文。
- 分版本迭代：先搭出可用、顺手、视觉舒服的基础框架，再逐步加入 AI API 绑定和具体识别场景。

## 2. 产品定位

「安排」模块可以理解为即我里的“未来事项中枢”。

它统一收纳以下内容：

- 用户主动创建的事项。
- 用户发给自己的备忘或计划。
- 私聊、群聊中由 AI 识别出的承诺、请求、约定或提醒。
- 和时间、地点、人物有关的未来行为。
- 可以由 AI 预处理、部分执行或完全执行的事项。
- 已经过期但用户还没有决定如何处理的事项。

它和传统工具的关键区别在于：

- 不要求每个事项都必须有严格截止时间。
- 不把过期视为强错误。
- 不要求用户对所有事项立刻做决定。
- 不只保存事项本身，还保存事项背后的对话来源和语义依据。
- 不只面向“用户自己做什么”，也可能面向“别人承诺为用户做什么”或“AI 可以替用户做什么”。

## 3. 目标用户体验

用户进入「安排」时，应该获得三种感受：

- 我知道最近有哪些真正值得注意的事情。
- 我可以快速把脑子里的事放进来，不需要先想清楚分类。
- 就算有很多没完成的旧事项，也不会被软件审判或压迫。

因此页面不宜做成传统任务软件的强管理感，而应该更接近一个温和的生活安排面板：

- 首页只突出少数重点安排。
- 过期事项不使用大面积红色制造焦虑。
- 提供“以后再说”这类符合真实心理的处理方式。
- 支持日历视角获得全局感，但不把日历变成唯一组织方式。
- 详情页强调来源、人物、时间、地点、状态和可执行动作。

## 4. 核心对象：安排项

安排项是模块中的基础数据单位。一个安排项不等同于一条消息，也不等同于一条待办。它可以由多条消息、多段对话、多个提醒和一次或多次用户操作共同构成。

建议安排项包含以下信息：

- 标题：用户能快速理解的安排摘要，如“明天到公司帮小李带早餐”。
- 类型：可弱化展示，内部可区分待办、日程、提醒、任务、AI 可执行事项等。
- 状态：待处理、进行中、已完成、已提醒、以后再说、已归档等。
- 时间信息：可为空，可以是截止时间、开始时间、结束时间、时间段、模糊时间或循环规则。
- 地点信息：可为空，如医院、公司、某个城市、线上会议等。
- 相关人物：发起人、执行人、受益人、参与人等。
- 来源：手动创建、发给自己、私聊识别、群聊识别、AI 建议等。
- 上下文：关联的消息、对话片段、识别理由和后续补充。
- 提醒设置：提前提醒、循环提醒、一次性提醒等。
- AI 执行能力：只能用户完成、AI 可预处理、AI 可完全执行。
- 优先级或关注度：不一定由用户手动设定，可由近期性、人物关系、时间明确度、对话强度等推断。

## 5. 创建机制

安排项需要同时支持手动创建和智能创建。

### 5.1 手动创建

手动创建是必须具备的基础能力，因为 AI 无法识别所有隐喻、暗号和用户个人习惯。

典型例子：

- 用户输入“～～”，但用户自己知道这代表“游泳”。
- 用户只想简单记一句“下周处理一下那个事”，暂时不想补全细节。
- 用户需要创建一个不适合从对话中自动推断的私人安排。

MVP 中手动创建至少应支持：

- 输入标题或内容。
- 可选时间。
- 可选地点。
- 可选备注。
- 保存后进入安排列表。
- 后续可完成、编辑、删除或以后再说。

### 5.2 智能创建

智能创建来自对话和文本识别，后续版本逐步实现。

主要来源包括：

- 发给自己。
- 私聊。
- 群聊。
- 用户主动输入的一段自然语言。
- 后续可能包括图片、语音、文件等多模态内容。

智能创建不应该一次性追求覆盖所有复杂场景。更适合一个场景一个场景打磨。

## 6. AI 识别场景

### 6.1 发给自己的安排

用户给自己发送“后天去一趟医院”，系统应识别出一条安排：

- 标题：后天去医院。
- 时间：后天。
- 地点：医院。
- 来源：发给自己。
- 状态：待处理。

这是最适合作为 AI 识别第一阶段的场景，语义链路短、用户预期明确、实现闭环清晰。

### 6.2 私聊中的承诺和请求

例子：

- 对方说：“明天来公司帮我带个早餐。”
- 用户回复：“好的。”

系统应识别：

- 在用户自己的安排模块中生成“明天到公司帮某某带早餐”。
- 在对方安排模块中可生成“某某明天来公司帮我带早餐”。

这里需要识别：

- 谁提出请求。
- 谁承诺执行。
- 执行对象是什么。
- 时间和地点是什么。
- 是否有明确同意行为。

### 6.3 连续对话中的多物品识别

私聊中可能不是一句话完成，而是连续对话不断补充：

- 对方让用户帮忙带 A。
- 后续又补充 B、C、D、E。
- 用户可能分多次回复确认。

系统最终需要识别的是一条或一组安排：“帮对方带 A、B、C、D、E 几个物品”，而不是机械地产生多条割裂事项。

这要求 AI 具备上下文聚合能力：

- 判断多个消息是否属于同一意图。
- 合并新增物品或条件。
- 保留来源消息。
- 避免重复创建。

### 6.4 群聊中的安排

群聊识别更复杂，因为可能涉及多个人、多角色和多个安排。

当前原始需求中尚未确定：

- 群聊安排是否只展示和用户自己相关的内容。
- 是否展示整个群聊中所有安排。

建议先采用保守策略：

- MVP 不做群聊 AI 自动识别。
- 第一版群聊识别只展示和当前用户明确相关的安排。
- 群聊中的公共安排可作为后续开关或独立视图。

### 6.5 相似安排的归集与合并

安排项不能简单按消息逐条生成，否则会产生大量重复。

例子：

- 用户计划后天去医院。
- 爸爸提醒：“一定记得去医院。”
- 用户回复：“好的，我已经有安排了。”
- 姐姐问身体情况。
- 用户回复：“我已经到医院挂号了。”

这些内容都应关联到同一条“去医院检查/就医”的安排中。

合并后，列表只展示一条核心安排，但详情页需要展示：

- 原始创建来源。
- 爸爸的提醒对话。
- 姐姐的关心对话。
- 用户已挂号的补充信息。
- AI 为什么判断它们相关。

### 6.6 完成状态的智能判断

安排项不能只依赖用户手动完成。

例子：

- 原有安排：去医院检查。
- 后续用户对姐姐说：“我今天上午去医院体检了，身体没啥情况。”

系统应识别该安排可能已经完成或状态已变化，并给出温和处理：

- 自动标记为可能已完成。
- 或提示用户“这条安排看起来已经完成，是否标记完成？”
- 或进入“已发生/待确认”状态。

建议避免完全静默地自动完成高风险事项，优先采用“AI 判断 + 用户确认”的方式。

## 7. 时间、日历与提醒

安排里的时间不应只有一种形态。

### 7.1 时间类型

至少需要考虑：

- 截止时间：任务、待办常见形式。
- 时间段：日程常见形式。
- 模糊时间：后天、周末、最近、有空时。
- 无时间：用户暂时不想设置时间。
- 循环时间：每周、每月、每天、工作日等。
- 提醒时间：某个安排发生前或发生时提醒用户。

### 7.2 日历呈现

和时间有关的安排需要进入日历视角，让用户获得全局总览。

日历视图应解决：

- 某天有哪些安排。
- 哪些是明确时间段。
- 哪些只是当天之前或当天附近需要关注。
- 哪些是提醒，而不是必须完成的任务。

MVP 可以先做列表和轻量日期分组，日历完整视图可放到后续版本。

### 7.3 提醒机制

提醒既可以是独立安排，也可以是安排项的附属机制。

需要区分：

- 用户创建一个提醒：到点提醒即可，不一定有完成概念。
- 用户创建一个任务或日程，并为其设置提醒。
- 用户设置提前提醒或循环提醒。

提醒发生后，不一定代表安排完成。产品状态需要避免混淆“已提醒”和“已完成”。

## 8. 完成、过期与“以后再说”

安排模块必须有良好的完成机制，否则事项会不断堆积，形成心理负担。

### 8.1 常规完成

用户应能用轻量方式完成安排：

- 勾选完成。
- 右滑完成。
- 详情页完成。
- 对 AI 建议的完成状态进行确认。

### 8.2 过期未完成

不能照搬传统任务软件：大量红色逾期提醒会制造焦虑，让用户想远离应用。

原始需求中的产品哲学是：

- 人生充满变数。
- 不按之前设定的轨迹完成，也完全可以。
- 很多任务没有按时完成，并不等于用户失败。

因此过期状态应更温和：

- 不大面积红色警告。
- 不强迫用户立即改期。
- 不强迫用户完成或删除。
- 提供一个符合直觉的“以后再说”动作。

### 8.3 以后再说

“以后再说”是一个重要交互。

它适合处理这些情况：

- 用户现在不能完成。
- 用户不想删除。
- 用户也不知道新的截止时间。
- 用户只是想先把它从当前压力区移开。

可能的交互：

- 长按出现“以后再说”。
- 右滑出现“以后再说”。
- 详情页提供“以后再说”按钮。

可能的状态逻辑：

- 从当前重点列表中降权。
- 移入“以后再说”分组。
- 保留原始时间和上下文。
- 后续可被搜索、恢复、重新安排。

## 9. AI 执行分层

安排项不仅是用户自己要做的事，也可能是 AI 可以参与执行的事。

可以按执行能力分三类：

- 用户必须亲自完成：如去医院、线下见面、帮人带东西。
- AI 可以提前辅助：如整理资料、生成路线、准备清单、草拟回复、查找信息。
- AI 可以直接完成：如自动生成一段文本、发送提醒、整理日程摘要。

不同类型应有不同操作：

- 用户亲自完成：提供提醒、上下文、完成确认。
- AI 辅助完成：提供“让 AI 先准备”。
- AI 直接完成：提供“交给 AI 执行”或“确认后执行”。

MVP 可先在数据和视觉上预留这个概念，不必立即做真实 AI 执行闭环。

## 10. API 绑定需求

原始需求明确提到：AI 识别机制需要允许每个用户输入自己的大模型 API，消耗自己的 Token。

这意味着后续版本需要一个 API 配置能力：

- 输入 API Key。
- 选择模型或服务商。
- 保存配置。
- 展示连接状态。
- 提供测试调用。
- 说明 Token 消耗由用户自己的 API 产生。

从实现节奏看，这不应放在最小版本的第一步。建议在基础安排模块可用后，再进入 AI 识别版本。

## 11. 推荐版本节奏

### V0.1：安排模块基础框架

目标是让「安排」成为一个真实可用的模块，而不是空壳。

建议实现：

- 底部或页面入口增加“安排”模块。
- 安排列表页。
- 手动创建安排。
- 安排详情页或编辑区。
- 完成安排。
- 删除或归档安排。
- 简单时间展示。
- 基础空状态和基础视觉打磨。

这一版重点考察：

- 对需求的基础理解。
- 页面结构是否清晰。
- 交互是否轻量。
- 视觉是否舒服。

### V0.2：时间与低压力处理

建议实现：

- 按时间分组。
- 今日、近期、以后再说等分区。
- 过期但不焦虑的展示方式。
- “以后再说”操作。
- 更优雅的完成动效或滑动操作。

这一版重点体现产品哲学：不制造任务焦虑。

### V0.3：API 绑定与发给自己识别

建议实现：

- 用户配置自己的大模型 API。
- 测试 API 是否可用。
- 从用户输入的自然语言中识别安排。
- 先做“发给自己”或“手动输入一句话让 AI 解析”的简单闭环。

这一版不要追求复杂多人对话，先把 AI 调用、解析、确认、生成安排的链路跑通。

### V0.4：私聊承诺识别

建议实现：

- 模拟私聊消息。
- 识别对方请求和用户确认。
- 生成和用户相关的安排。
- 保留消息上下文。
- 支持用户确认或修正 AI 识别结果。

### V0.5：合并与详情上下文

建议实现：

- 相似安排合并。
- 详情页展示关联对话。
- AI 给出合并理由。
- 用户可以手动拆分或合并。

### V0.6：群聊与高级状态

建议实现：

- 群聊中和用户相关的安排识别。
- 多人角色识别。
- 自动判断可能已完成。
- AI 辅助执行分层。

群聊全量安排展示和复杂执行闭环可以继续后置。

## 12. MVP 建议范围

如果当前时间有限，最小可用版本建议只做：

- 新增“安排”入口。
- 安排列表。
- 手动创建安排。
- 可选时间、地点、备注。
- 完成安排。
- “以后再说”。
- 安排详情展示基础信息。
- 用少量静态示例体现未来 AI 识别方向。

不要在第一版强行做：

- 完整大模型 API 调用。
- 复杂私聊群聊识别。
- 多人双向安排同步。
- 完整日历。
- 自动完成判断。
- AI 自动执行真实动作。

原因是第一版最重要的是让模块成立、可用、顺手，并展示出对产品哲学的理解。

## 13. 关键体验原则

实现时建议坚持以下原则：

- 列表只突出少数真正需要关注的安排。
- 手动创建流程越短越好。
- 不要求用户先选复杂类型。
- 过期事项要温和，不要刺眼警告。
- “以后再说”应该是一级重要操作。
- AI 识别结果必须允许用户确认和修改。
- 详情页要解释“为什么这条安排存在”。
- 和人有关的信息要被看见。
- 时间明确和时间模糊的事项都要能存在。
- 不为了功能数量牺牲可用性。

## 14. 未决问题

以下问题原始需求中还没有完全定论，需要在后续实现中逐步判断：

- 群聊中是否展示所有安排，还是只展示和当前用户相关的安排。
- AI 自动完成安排时，哪些场景可以直接完成，哪些必须用户确认。
- 过期事项多久后进入“以后再说”或低关注区。
- 用户 API Key 的安全保存方式。
- 安排项类型是否需要显式展示给用户。
- 多人安排是否需要真正同步到对方账户，还是先只在本地模拟。
- 日历视图在第一阶段是完整月历，还是轻量日期分组。

## 15. 我的实现取舍建议

如果把这段需求转化为本项目的下一步开发，我建议优先做一个打磨好的 V0.1 + V0.2：

- 先把「安排」模块作为真实页面加入 Demo。
- 把手动创建、完成、以后再说做顺。
- 用视觉和交互体现“低压力安排管理”。
- 详情页预留来源、人物、时间、地点、上下文结构。
- 再用一两个静态示例或模拟识别入口，为后续 AI 版本留空间。

这样既能体现对原始需求的理解，也能在有限时间内交付一个用户可以真实体验的版本。
