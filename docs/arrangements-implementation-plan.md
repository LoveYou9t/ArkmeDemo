# 即我「安排」模块软件实施方案

## 1. 实施目标

本方案把「安排」模块从产品需求落到当前 ArkmeDemo 的软件实现层面。目标不是一次性做完所有 AI 场景，而是先交付一个可体验、可扩展、符合即我移动端气质的初始版本。

初始版本应做到：

- 在移动端 Demo 中新增一个真正可进入的「安排」模块。
- 用户可以手动创建安排。
- 用户可以查看安排列表和安排详情。
- 用户可以完成、以后再说、恢复或归档安排。
- 页面视觉延续当前 Demo 的灰白底、绿色主色、轻量卡片和移动端壳层。
- 数据模型预留 AI 识别、对话来源、合并、日历、提醒和 API 绑定能力。

## 2. 当前项目接入点

当前项目结构对「安排」的接入比较直接：

- `src/App.tsx` 中 `PageType` 目前为 `"records" | "insight" | "mine"`。
- `src/pages/Home.tsx` 负责底部主 Tab、首页、侧边栏、快记、洞见、我的等主要移动端界面。
- `src/settings/preferences.ts` 管理 Tab 文案、多语言文案、主题和强调色。
- `src/styles/tokens.css` 已有移动端主题 token、浅色/暗色变量、主色变量和卡片阴影。

建议第一版新增：

- `PageType` 增加 `"arrangements"`。
- 底部导航增加「安排」Tab。
- `Home.tsx` 中新增 `ArrangementsScreen`。
- 独立新增数据和类型文件，避免继续膨胀 `Home.tsx`。

建议文件拆分：

- `src/types/arrangement.ts`：安排项类型定义。
- `src/data/arrangements.ts`：初始示例、localStorage 读写、状态工具方法。
- `src/pages/Arrangements.tsx`：安排模块主页面。
- `src/components/arrangements/ArrangementCard.tsx`：安排列表项。
- `src/components/arrangements/ArrangementDetailSheet.tsx`：详情底部弹层。
- `src/components/arrangements/ArrangementEditorSheet.tsx`：创建/编辑底部弹层。

如果时间很紧，也可以先把页面组件写在 `Home.tsx` 内部，但数据类型建议仍拆出去，给后续 AI 识别留接口。

## 3. 初始数据模型

安排项不应只是一条待办。它需要承载时间、人物、地点、来源和后续 AI 上下文。

建议 TypeScript 类型：

```ts
export type ArrangementStatus =
  | "active"
  | "done"
  | "later"
  | "archived";

export type ArrangementTimeKind =
  | "none"
  | "deadline"
  | "timeRange"
  | "reminder"
  | "fuzzy";

export type ArrangementSourceType =
  | "manual"
  | "sendToSelf"
  | "privateChat"
  | "groupChat"
  | "aiSuggestion";

export type ArrangementAiCapability =
  | "userOnly"
  | "aiAssist"
  | "aiExecutable";

export type ArrangementSourceRef = {
  id: string;
  type: ArrangementSourceType;
  title: string;
  excerpt: string;
  createdAt: number;
  conversationId?: string;
  messageId?: string;
};

export type ArrangementItem = {
  id: string;
  title: string;
  note?: string;
  status: ArrangementStatus;
  timeKind: ArrangementTimeKind;
  startAt?: number;
  endAt?: number;
  fuzzyTimeLabel?: string;
  location?: string;
  people: string[];
  sourceType: ArrangementSourceType;
  sourceRefs: ArrangementSourceRef[];
  aiCapability: ArrangementAiCapability;
  attentionScore: number;
  createdAt: number;
  updatedAt: number;
  completedAt?: number;
  laterAt?: number;
};
```

第一版 UI 不需要展示所有字段，但数据模型要保留字段，后续才能平滑接入 AI 识别、合并、日历和提醒。

## 4. 本地存储方案

第一版无后端，建议使用 localStorage：

- key：`arkme-demo.arrangements`
- 存储完整 `ArrangementItem[]`
- 初始化时合并几条 Demo 示例和用户真实创建项
- 写入失败时保留内存状态，不阻塞页面操作

建议状态更新方法：

- `createArrangement(input)`
- `updateArrangement(id, patch)`
- `completeArrangement(id)`
- `moveArrangementToLater(id)`
- `restoreArrangement(id)`
- `archiveArrangement(id)`

后续接入后端时，可以把这些方法替换成 repository/service 层，页面组件不直接感知存储方式。

## 5. 初始界面信息架构

### 5.1 底部导航

底部导航从三项扩展为四项：

- 快记
- 安排
- 洞见
- 我的

「安排」建议放在「快记」之后，因为它与快记和发给自己的记录关系最强。

如果担心底部四项拥挤：

- Tab 图标尺寸保持 22-24px。
- 文案使用 11-12px。
- 当前项目底部栏留白较充足，四项可接受。

### 5.2 安排首页结构

首屏建议结构：

```text
┌─────────────────────────┐
│ 安排                 ＋ │
│ 未来的事，轻一点放在这 │
├─────────────────────────┤
│ 今天值得留意              │
│ [去医院复查]              │
│ 明天 09:30 · 医院 · 爸爸提醒 │
├─────────────────────────┤
│ 分段筛选                  │
│ 全部 / 近期 / 以后再说 / 已完成 │
├─────────────────────────┤
│ 本周                      │
│ [帮小李带早餐]            │
│ 明天 · 公司 · 来自私聊      │
│                           │
│ [整理面试项目 README]      │
│ 无明确时间 · AI 可协助      │
├─────────────────────────┤
│ 更早 / 以后再说 / 已完成    │
└─────────────────────────┘
```

页面应该是信息密度适中的移动端工具页，不做营销式 Hero，也不把说明文案做得太重。

### 5.3 顶部区域

顶部使用普通页面标题，不建议做大面积装饰：

- 标题：`安排`
- 副标题：`未来的事，轻一点放在这`
- 右侧操作：新增按钮 `+`

新增按钮点开底部创建弹层。

### 5.4 关键概览区

顶部下方可以放一个“今天值得留意”区，只展示 1-2 条高关注安排：

- 明确今天或明天发生。
- 有人明确提醒或涉及承诺。
- AI 判断需要用户确认。

如果没有高关注安排，显示温和空状态：

- `现在没有必须立刻处理的安排`
- 不使用“暂无任务”这种任务软件语气。

### 5.5 筛选分段

建议初始分段：

- `全部`
- `近期`
- `以后再说`
- `已完成`

不要第一版就加入复杂分类筛选。安排的产品哲学是弱化类型，先让用户轻松看见和处理。

### 5.6 列表分组

列表按低压力时间分组：

- 今天
- 明天
- 本周
- 以后
- 无明确时间
- 以后再说
- 已完成

过期未完成不单独做刺眼红色分组。可以温和显示为：

- `原计划 昨天`
- `可以重新安排`
- `以后再说`

## 6. 安排卡片样式

卡片应延续当前 Demo 风格：

- 背景：`var(--surface)`
- 圆角：8-12px，建议 12px
- 边框：`var(--border-light)` 或透明
- 阴影：轻量 `var(--mine-card-shadow)` 或无阴影
- 内边距：12px
- 卡片之间间距：8px

卡片内容结构：

```text
┌─────────────────────────┐
│ ○  明天到公司帮小李带早餐 │
│    明天 09:00 · 公司       │
│    小李 · 来自私聊          │
│    [AI已识别] [可提醒]      │
└─────────────────────────┘
```

建议字段：

- 左侧状态按钮：空心圆表示待处理，绿色勾表示已完成。
- 主标题：一行或两行，超出截断。
- 时间地点行：有时间地点则展示，无时间则展示“还没有时间”。
- 人物来源行：展示相关人物和来源。
- 标签行：展示 `AI建议`、`可提醒`、`以后再说`、`AI可协助` 等。

卡片操作：

- 点击卡片：打开详情。
- 点击圆圈：完成或恢复。
- 长按：打开快捷操作菜单。
- 右滑：露出 `完成` 和 `以后再说`。

初始版本如果不做手势，也要在详情里提供这些动作。

## 7. 创建安排弹层

创建入口点击 `+` 后，从底部弹出创建弹层。

初始字段：

- 内容：必填，多行输入。
- 时间：可选，支持快捷选项。
- 地点：可选。
- 相关人：可选。
- 备注：可选。

快捷时间选项：

- 今天
- 明天
- 本周
- 没有时间

底部主操作：

- `保存安排`

次要操作：

- `取消`

文案风格应轻，不要像项目管理工具：

- 输入 placeholder：`写下接下来可能要做的事`
- 时间为空提示：`不确定时间也可以先放进来`

## 8. 安排详情页

详情建议使用底部 Sheet 或全屏详情页。第一版可先用底部 Sheet，和当前快记详情交互保持一致。

详情内容：

- 标题
- 状态
- 时间
- 地点
- 相关人
- 来源
- 备注
- 关联上下文
- 后续能力占位

详情操作：

- 完成
- 以后再说
- 编辑
- 删除/归档
- 恢复

上下文区域即使第一版只展示静态示例，也应留出结构：

```text
相关上下文
来自发给自己：后天去一趟医院
来自爸爸：一定记得去医院，知道吗？
来自姐姐：你这个身体情况怎么办的？
```

这会帮助后续 AI 合并和对话溯源自然接入。

## 9. “以后再说”交互

「以后再说」是本模块最能体现产品理解的动作，应该作为一级能力设计。

第一版处理方式：

- 在卡片长按菜单中出现。
- 在详情页作为次级按钮出现。
- 点击后状态变为 `later`。
- 该安排从近期列表移入「以后再说」分组。
- 保留原始时间，不强迫用户重新选择时间。

展示方式：

- 轻灰标签：`以后再说`
- 不显示红色过期警告。
- 可在「以后再说」分组中点击恢复。

恢复方式：

- 详情页点击 `重新放回安排`
- 恢复到 `active`

## 10. 完成机制

第一版以手动完成为主：

- 点击卡片左侧圆圈完成。
- 详情页点击完成。
- 已完成安排进入「已完成」分组。

完成后的视觉：

- 标题变为较浅文字。
- 显示完成时间。
- 不建议整卡完全隐藏，避免用户不知道操作结果。

后续 AI 完成判断预留：

- 新增 `suggestedStatus` 或 `aiCompletionSignal` 字段。
- 如果 AI 判断可能完成，卡片显示 `可能已完成`。
- 用户确认后才改为 `done`。

## 11. 初始 Demo 数据

建议内置 4 条示例，帮助面试官一进页面就理解模块：

1. `后天去医院复查`
   - 时间：后天
   - 地点：医院
   - 人物：爸爸、姐姐
   - 来源：合并了 3 段对话
   - 体现：上下文合并

2. `明天到公司帮小李带早餐`
   - 时间：明天上午
   - 地点：公司
   - 人物：小李
   - 来源：私聊识别
   - 体现：承诺识别

3. `整理安排模块第一版交互`
   - 时间：无明确时间
   - AI 能力：AI 可协助
   - 来源：手动创建
   - 体现：AI 辅助执行分层

4. `给自己设置周末游泳提醒`
   - 时间：周末
   - 来源：手动创建
   - 状态：以后再说
   - 体现：隐喻/私人习惯需要手动创建

这些示例不代表真实后端识别，只用于展示未来能力。

## 13. 后续扩展空间

### 13.1 AI API 绑定

后续新增设置入口：

- 入口位置：我的 > 设置 > AI 能力，或安排页右上角设置。
- 字段：服务商、Base URL、API Key、模型名称。
- 操作：测试连接、保存、清除。
- 提示：Token 由用户自己的 API 消耗。

数据预留：

```ts
type AiProviderConfig = {
  provider: "openaiCompatible" | "openai" | "custom";
  baseUrl?: string;
  apiKeyMasked: string;
  model: string;
  enabled: boolean;
};
```

### 13.2 发给自己识别

当前项目已有“发给自己”对话和记录结构，可以作为第一条 AI 识别链路：

- 用户在发给自己里输入一句自然语言。
- 识别为候选安排。
- 用户确认后进入安排模块。
- 原消息作为 `sourceRefs` 保存。

建议交互：

- 在发给自己详情或快记详情里出现 `转为安排`。
- AI 可用后出现 `AI 识别安排`。

### 13.3 私聊识别

当前项目已有消息测试后台和测试私聊/群聊数据，可以用于模拟：

- 从测试私聊消息中读取上下文。
- 识别请求、承诺、人物、物品和时间。
- 生成待确认安排。

第一阶段只处理：

- 对方请求。
- 用户明确回复“好的/可以/没问题”。
- 单个安排。

第二阶段再处理连续多物品 A、B、C、D、E。

### 13.4 群聊识别

建议后置。

扩展时先做：

- 只展示和当前用户明确相关的安排。
- 提供“查看群聊其他安排”的入口。
- 不默认把整个群聊所有安排塞进用户列表。

### 13.5 合并机制

后续新增：

- `mergedIntoId`
- `relatedArrangementIds`
- `sourceRefs`
- `aiMergeReason`

交互上：

- 详情页显示“这条安排关联了 3 段上下文”。
- 用户可拆分。
- 用户可手动合并两条安排。

### 13.6 日历视图

后续可在安排页顶部增加视图切换：

- 列表
- 日历

日历不应替代列表，只负责全局总览：

- 用小点或轻标签表示当天安排数量。
- 点击某天展示当天安排。
- 无明确时间的安排不强行塞进日历。

### 13.7 提醒机制

后续可以加：

- 提前 10 分钟、30 分钟、1 小时、1 天。
- 自定义提醒。
- 循环提醒。
- 浏览器通知权限。

状态上要区分：

- 已提醒
- 已完成
- 已错过

提醒发生不等于任务完成。

### 13.8 AI 执行层

后续根据 `aiCapability` 分层：

- `userOnly`：只展示上下文和提醒。
- `aiAssist`：显示 `让 AI 先准备`。
- `aiExecutable`：显示 `交给 AI 处理`。

第一批可执行能力可以很轻：

- 生成准备清单。
- 草拟回复。
- 总结相关上下文。
- 给出下一步建议。

## 14. 初始视觉建议

### 14.1 颜色

沿用项目现有变量：

- 背景：`var(--bg)`
- 卡片：`var(--surface)`
- 主色：`var(--primary)`
- 次级文字：`var(--text-tertiary)`
- 柔和主色底：`var(--primary-soft)`

不要把安排页做成大面积绿色。绿色只用于状态、主操作和轻标签。

### 14.2 排版

建议字号：

- 页面标题：20px，600
- 卡片标题：15-16px，600
- 元信息：12-13px
- 标签：10-11px

行高保持舒展，避免任务软件的压迫感。

### 14.3 圆角

当前项目中有 10-12px 的常用卡片圆角。安排页可以使用：

- 卡片：12px
- 标签：999px 或 8px
- 底部 Sheet：顶部 22px

### 14.4 图标

如后续引入图标，建议使用 lucide-react：

- Plus：新增
- Check：完成
- Clock：时间
- MapPin：地点
- UserRound：人物
- Sparkles：AI
- CalendarDays：日历
- Bell：提醒
- MoreHorizontal：更多

如果不新增依赖，也可以先使用简单内联 SVG，但后续统一为 lucide 更利于维护。

## 15. 工程迭代顺序

建议按以下顺序开发：

1. 新增类型和本地数据层。
2. 新增 `arrangements` PageType 和底部 Tab 文案。
3. 新增安排页面静态布局。
4. 接入 localStorage 状态。
5. 实现创建弹层。
6. 实现详情弹层。
7. 实现完成、以后再说、恢复、归档。
8. 加入示例上下文展示。
9. 跑移动端页面检查和 `pnpm verify:answer`。

这样每一步都有可见增量，出问题也容易回退。

## 16. 第一版验收标准

第一版完成后，应该能验证：

- 底部导航可以进入安排页。
- 安排页首屏能看出这是“未来事项中枢”，不是普通待办列表。
- 用户能新增一条安排，并刷新后保留。
- 用户能完成一条安排。
- 用户能把安排标记为以后再说。
- 用户能打开详情看到时间、地点、人物、来源和上下文结构。
- 页面没有大面积红色逾期压迫感。
- 页面风格与当前即我 Demo 保持一致。
- 后续 AI 识别、API 绑定、日历和提醒都有明确接入位置。

## 17. 建议第一轮实际交付范围

如果下一步进入编码，我建议第一轮实际交付：

- 新增「安排」Tab。
- 新增 `src/pages/Arrangements.tsx`。
- 新增 `src/types/arrangement.ts` 和 `src/data/arrangements.ts`。
- 实现列表、创建、详情、完成、以后再说。
